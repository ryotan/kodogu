# ADR-0001: アーキテクチャ決定を記録する

## ステータス

承認済み

## 背景

プロジェクトで行われたアーキテクチャ決定を記録する必要がある。アジャイルプロジェクトにおけるアーキテクチャは、従来のアーキテクチャドキュメントとは異なる方法で記述・定義される必要がある。アーキテクチャ決定は以下の特性を持つべき：

- **追跡可能**: なぜその決定が行われたかを理解できる
- **可逆的**: 決定を覆す場合に何を変更すべきかを文書化
- **協調的**: すべてのチームメンバー（AI エージェントを含む）がアクセス可能
- **タイムリー**: 決定が新鮮なうちに記録

## 決定

アーキテクチャ決定記録（ADR: Architecture Decision Records）を使用して、構造、非機能特性、依存関係、インターフェース、構築技術に影響を与える、アーキテクチャ的に重要な決定を文書化する。

**ADR フォーマット:**

各 ADR は以下を含む：

1. **タイトル**: 短い説明的な名前（例：「レイヤー境界での Translator 使用」）
2. **ステータス**: 提案中、承認済み、非推奨、置換済み
3. **背景**: 取り組んでいる課題は何か？
4. **決定**: 提案・実施する変更は何か？
5. **結果**: その結果、何が容易になり、何が困難になるか？

**配置場所:**

- ADR は `docs/adr/` に保存
- 連番で命名: `0001-タイトル.md`, `0002-タイトル.md` など
- `docs/adr/README.md` にリスト化

**ADR を書くべきとき:**

- 新しいアーキテクチャパターンや原則を導入する
- 複数のアーキテクチャアプローチから選択する
- 横断的関心事（エラー処理、データ変換など）を決定する
- 複数モジュールに影響する技術選択を行う
- アーキテクチャ哲学を反映したコーディング規約を確立する

**ADR を書くべきでないとき:**

- 単一モジュール内の実装詳細
- アーキテクチャを変更しないバグ修正
- 既存パターンに従った定型的な機能追加

## 結果

### 良い影響

- **明確性**: 将来の開発者（人間・AI）がアーキテクチャ選択の「なぜ」を理解できる
- **一貫性**: 決定が可視化され、参照可能
- **オンボーディング**: 新規コントリビューターがアーキテクチャ哲学を迅速に学べる
- **進化**: 決定を再検討する際に何を変更すべきか容易に特定できる

### 悪い影響

- **オーバーヘッド**: ADR 執筆に時間がかかる
- **メンテナンス**: ADR が古くなる可能性がある

### 軽減策

- ADR は簡潔に保つ（最大 1-2 ページ）
- 「なぜ」に焦点を当て、「どのように」（実装詳細）はコードに記述
- 置換済み ADR は削除せず、明確にマークする
